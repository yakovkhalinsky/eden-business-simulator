# Cafe Business Simulator Plan

Goal: `c63ef3b9-3903-471b-85b9-26c22feb83f8`

Add a non-technology business domain (cafe/hospitality) to the Eden Business Simulator
framework. Fully research the systems and data generated by a real cafe, and expand
simulator capabilities so that adding future business types is easier.

## Cafe/hospitality domain findings

### Operational workflow

1. **Open** — count float, equipment startup, staff clock-in, initial stock.
2. **Prep** — load pastry case, prep ingredients, activate KDS stations.
3. **Service** — POS order → KDS routing → preparation → expo/serve → payment → loyalty.
4. **Close** — clean, count float, cash/card reconciliation, waste log, reorder, clock-out.

### Systems used

- POS / order capture (counter, handheld, kiosk, QR, online, delivery aggregators)
- Kitchen Display System (KDS) — routes tickets to bar/kitchen/pastry stations
- Inventory / recipe BOM — ingredient-level stock, recipe costing, purchase orders, deliveries
- Rostering / time clock — schedules, roles, clock-in/out, labor cost
- Reservations / table management
- Loyalty / CRM
- Payments / accounting — cash drawer, card/mobile payments, tips, Z-report, reconciliation
- Supplier / procurement

## Extensibility gaps and proposed framework helpers

1. **Declarative event-probability DSL** — replace hand-coded weight tables with a
   `WeightedEventCatalog` that supports base weights plus state guards and time-of-day modifiers.
2. **Actor / entity templates** — reusable `ActorPool`, `MenuCatalog`, `StaffRoster`,
   `SupplierLedger` with deterministic ID generation.
3. **State machine mixin** — generic lifecycle helper for order/ticket status transitions
   (NEW → PREPARING → DONE, etc.).
4. **Daypart scheduler** — vary event weights by simulated clock hour so cafes have
   breakfast/lunch rushes and a close phase.
5. **Recipe / BOM inventory ledger** — auto-deduct ingredients when items are prepared,
   support stock counts and wastage.
6. **Correlation helper** — deterministic linked IDs across order → payment → ticket →
   loyalty events.
7. **Initial-state loader** — standardize `initial_staff`, `initial_menu_items`,
   `initial_suppliers`, `opening_float`, etc.

These helpers should live under a new package (suggested
`src/eden_business_simulator/framework/` or `utils/`) and be documented in
`docs/adding_a_business.md`.

## Recommended implementation approach

Implement option B: build the cafe simulator **and** the reusable helpers together.

1. Add a `framework/` package with:
   - `catalog.py` — `WeightedEventCatalog`
   - `actors.py` — `ActorPool`, `StaffRoster`, `MenuCatalog`
   - `inventory.py` — `InventoryLedger` with recipe BOM support
   - `scheduler.py` — `DaypartScheduler`
   - `state_machine.py` — `TransitionModel`
   - `ids.py` — deterministic slug+seed ID helpers
2. Refactor `EcommerceSimulator` minimally to prove helpers are reusable and do not
   break the existing event contract.
3. Add `CafeSimulator` in `src/eden_business_simulator/businesses/cafe.py`.
4. Register it in `businesses/__init__.py`.
5. Add `tests/test_cafe.py` and `tests/test_framework_*.py`.
6. Update `README.md` and `docs/adding_a_business.md`.

## Options considered

| Option | Description | Pros | Cons | Verdict |
|---|---|---|---|---|
| A | Hand-code cafe like ecommerce | Fast, low churn | Duplicates boilerplate, no future leverage | Not recommended |
| B | Build cafe + reusable helpers | Proves helpers with a real domain, immediate extensibility | Slightly more upfront design | **Recommended** |
| C | Fully declarative/YAML engine first | Maximum future extensibility | High risk, heavy, delays cafe | Not recommended now |

### Deviations / notes

1. **EcommerceSimulator left unchanged.** The optional refactor to prove helpers are
   reusable was skipped because retrofitting `WeightedEventCatalog`/`IdGenerator` risked
   changing the deterministic event sequence and breaking the existing ecommerce test
   suite. The helpers are proven reusable through the cafe simulator and the dedicated
   framework tests instead.
2. **Setup events are forced before catalog selection.** The first ~20 events of a
   cafe run are emitted from a deterministic setup queue (`shift_opened`, staff clock-ins,
   menu items, supplier deliveries). This guarantees that the simulator can take orders
   immediately after setup and keeps ID ordering reproducible.
3. **Shift close timing is duration-relative.** `shift_closed` is forced when the
   simulated clock is within four ticks of `config.duration_seconds`. This keeps the
   close event inside a normal run while preserving the existing runner contract that
   the simulator does not know wall time.
4. **EventEnvelope contract unchanged.** All cafe events are still returned as
   `{"event_type": ..., "payload": ...}` and wrapped by the runner with `version = "1.0"`.
5. **RecipeComponent includes a `name` field.** The research payload examples already
   included a human-readable ingredient name; the helper dataclass was adjusted to match.
